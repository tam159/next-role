An analytics, BI & ML platform that grows from laptop to enterprise

One stack, finalized on day one — dlt into a ClickHouse medallion warehouse, dbt, a Cube semantic layer, and Superset — the same containers from laptop to production, with customer-owned warehouses joining only at the enterprise edge. Everything the platform collects feeds two improvement loops: fine-tuned small models, and an optimizer agent that tunes the career agent itself.

The stack at a glance

TL;DR — same architecture at every scale, swap only the engine

Everything in this plan — extraction, transformation, metrics, permissions, BI, the analytics agent — is open source and joins the compose stack you already operate, on day one. This revision collapses the first draft's phase-by-phase tool ladder: ClickHouse, Dagster, Cube, and Superset are the stack from the first commit, so nothing gets migrated later — phases now add capacity and governance, not tools. The multi-warehouse adapters (dlt destinations, dbt adapters, Cube drivers) stay in the design for exactly one reason: enterprise tenants who bring their own warehouse. And the platform's end state is a flywheel — the warehouse feeds fine-tuned small models and an optimizer agent that continuously tunes the career agent.

The permissions doctrine — two locks. (1) The Cube security context is the primary lock: per-end-user, fail-closed, and portable — it behaves identically over DuckDB, ClickHouse, and any customer warehouse, which is what makes the analytics agent shippable. (2) Engine-native RLS/masking is the second lock, covering any path that bypasses the semantic layer — and with ClickHouse as the day-one engine, its row policies exist from day one too (BigQuery/Snowflake/ Databricks policies take over on BYO tenants). The agent never holds warehouse credentials, and prompt-level "permissions" are not permissions.

Ground truth

What the operational data looks like today

Explored live on postgres · next-role (PostgreSQL 18, pgvector image): 17 tables in public, split between the vendored LangGraph runtime and Better Auth identity tables. What you can measure on day one — before adding any instrumentation

  • Usage: DAU/WAU/MAU and login retention from session; threads & runs per user per day from thread/run + owner.
  • Reliability: run success / interrupt / error rates; run duration from created_at → updated_at; error threads.
  • Cost: tokens in/out per message from usage_metadata (verified present on every AI message), rolled up to cost per run, per user, per model — including the model-override choices sitting in run.kwargs.config.configurable.
  • Agent behavior: steps per run, node/subagent frequency, interrupt (HiL approval) rates from checkpoints.metadata.
  • Output: artifacts produced per thread from thread.values.files (resume YAML/PDF, recon docs, battlecards) and object-storage inventory.

What's missing — and where it should come from

  • Frontend behavior (page views, clicks, upload funnel, feature discovery, download events): nothing is instrumented today → product analytics.
  • Per-node latency and full traces: LangSmith tracing is configured today (LANGCHAIN_TRACING_V2), but its bulk export is now Enterprise-gated — the flywheel section moves the trace store to self-hosted Langfuse (MIT), which runs on services this stack already has.
  • Business events (signup → activation → habit): derivable once auth is on and events are landed in the warehouse.
  • Explicit feedback signals (thumbs on artifacts, edit-request outcomes): not captured today — they become the labels for the fine-tuning flywheel, so they join the event taxonomy below.
PII map (this drives governance): user.email/name, session.ipAddress/userAgent, CV/JD text inside thread.values.messages and checkpoint blobs, memories in store.value, and uploaded documents in object storage. The warehouse plan deliberately lands structure and metrics, not document bodies — raw chat/CV text stays out of analytics by default.

Target design

Architecture: ELT into a medallion warehouse, governed at the semantic layer

Five principles, then the picture:

  1. ELT, not ETL. Land raw JSON as-is (bronze), flatten and type it inside the warehouse with dbt. JSONB payloads evolve with the app; transformation-in-warehouse means schema drift lands safely instead of breaking extractors.
  2. One stack you operate; adapters for warehouses you don't. ClickHouse is the engine at every scale you run yourself — dev compose and production differ by hardware, not dialect, so dbt models are tuned exactly once. dlt, dbt, and Cube keep their multi-warehouse adapters for one purpose: enterprise tenants who bring BigQuery/Snowflake/Databricks.
  3. The warehouse is the source of truth. Product-analytics events flow into it (PostHog batch export); the PostHog UI is a lens, never a silo.
  4. Governance rides the pipeline. PII tags live in dbt meta, propagate to the catalog and to masking policies; lineage is emitted by dbt + the orchestrator, not documented by hand.
  5. The analytics agent never writes raw SQL against the warehouse. It queries the semantic layer with the end user's security context, so permissions are enforced in one portable place.

The engine

Warehouse: ClickHouse from day one; customer warehouses at the edge

Decision update. The first draft staged DuckDB + DuckLake → ClickHouse → cloud. Review verdict: one engine beats two migrations. The expensive part of a warehouse migration was never the connection string — it's the SQL dialect and the physical-design rework (dbt incremental strategies, table engines, type quirks) plus re-validating every model. Committing to ClickHouse OSS from the first commit removes that entirely: it's free, Apache-2.0, runs as one more compose container for local dev, and is the engine the stack would have graduated to anyway. What you accept: one always-on service (~2–4 GB locally) instead of an in-process library, and ClickHouse's quirkier dialect learned once. What you get: dev = prod parity, engine-enforced row policies from day one, PostHog-scale event ingestion, and zero engine swaps on the roadmap. DuckDB doesn't disappear — it's demoted to what it's genuinely best at: an ad-hoc notebook engine over Parquet exports, not a warehouse tier.

First, the idea to retire: analytics inside the operational Postgres

The "Postgres with a columnar extension" category effectively shook out in 2025–26 — three of the six candidates died or changed hands in ~18 months. Beyond project risk, two structural reasons: heavy scans contend with LangGraph's checkpoint write traffic, and an analytics agent issuing SQL against the OLTP database is a blast-radius problem. ELT out — even a nightly copy to Parquet — buys isolation, cheap storage, and the governance seam everything else in this plan attaches to.

Decision update: Dagster from day one. The first draft staged cron → Dagster; the same no-later-migration logic that picked ClickHouse applies here. The cost is genuinely small: two containers (webserver + daemon) that reuse the existing Postgres for run storage (dagster-postgres pointed at a separate database on the same instance). In exchange, dlt sources and dbt models are software-defined assets from the first pipeline run — schedules, retries, backfills, and the lineage graph exist before you need them. Everything underneath stays plain CLI/Python, so cron/GitHub Actions remains the emergency-simple fallback, but it's no longer a phase of the plan.

Transformation: dbt Core — with eyes open about the consolidation

  • dbt Core stays the pick. The Fivetran–dbt Labs merger (announced 2025-10-13, closed 2026-06-01) went toward openness: the Rust Fusion engine was relicensed Apache-2.0 and merged as dbt Core v2.0 (alpha); 1.x remains Apache-2.0 and maintained. Use 1.x now, move to v2 when stable for the parse-speed win.
  • The adapter: dbt-clickhouse is ClickHouse-maintained, Apache-2.0, and marked production/stable (v1.10.x, tracking dbt-core 1.10; incremental strategies: append, delete+insert, microbatch). It's the one dialect the project ever tunes — written once, validated against the same engine dev and prod. Stay on dbt Core 1.x here; the Fusion adapter is still alpha.
  • Hedge: SQLMesh was donated to the Linux Foundation (2026-03-25) and can consume dbt projects — keep models in portable SQL and off Cloud-only features and the exit stays open.

"dbt already has tests — do we really need elementary?"

They're different layers, and the adoption order matters. dbt tests are the assertions: they pass/fail a build, and their results evaporate into run_results.json. elementary (Apache-2.0) is a dbt package, not a service: it persists every test and run result as warehouse tables, adds anomaly tests plain dbt can't express (volume, freshness, distribution drift, schema changes), renders the edr HTML report — exactly the "dashboard UI for test results" you were guessing at — and pushes Slack alerts. So: dbt tests from the first model; add elementary the week you first wish test results had history. Bonus that pays off later: because its results live in the warehouse, the optimizer agent can query pipeline health like any other mart. Still avoid Soda Core v4 (ELv2 since 2026-01, awkward to embed in a product you ship) and GX (stewardship in flux: GX Cloud discontinued 2026-06, Fivetran taking over the OSS).

Shaping the data

Modeling: medallion layers, star-schema marts

Medallion answers "how raw is this table?"; star schema answers "how do I query the gold layer?". They compose — and the layer boundaries are exactly where governance attaches.

LayerSchemasOwnerRulesAccess
bronze raw_app · raw_posthog · raw_langsmith dlt / batch export As landed + load metadata. Append/merge only, schema-evolving, 30–90 day retention, pseudonymized identifiers Pipeline + admin only
silver staging · intermediate dbt (stg_*, int_*) Typed, deduped, conformed entities; PII columns tagged in meta and masked/hashed; one model per source entity Analysts + pipeline
gold marts dbt (fct_*, dim_*) Star schema; enforced contracts (contract.enforced: true); exposures declare Cube/BI/agent consumers; documented 100% BI, Cube, agent (via Cube)

Star, snowflake, or one big table?

  • Star for the marts. Fewer joins, simpler mental model — and markedly friendlier to an LLM agent than a normalized snowflake: every metric is one fact table plus named dimensions.
  • Snowflake only where a hierarchy earns it (none in sight yet — company/role taxonomies might qualify later).
  • One-big-table is a fine accelerant for a specific dashboard, but keep conformed dims underneath — Cube models want stable joins, and OBT ossifies badly once an agent depends on it.
  • ClickHouse physical design, decided once: facts on MergeTree ordered by (date, user); dlt merge loads land on ReplacingMergeTree; let dbt-clickhouse own engine/order-by config in model YAML instead of hand-written DDL.

Metrics & the agent

Semantic layer: yes to Cube — self-hosted Cube Core

Your instinct is right, with one sharp caveat. Cube Core (Apache-2.0, self-hosted) is the only option today that gives all three things the analytics agent needs, for free: programmatic metric discovery (/v1/meta), governed queries with per-end-user row-level security enforced server-side (JWT securityContext + queryRewrite + declarative access policies), and no raw SQL — the agent emits Cube's JSON query language or SQL against Cube views over the Postgres-wire API. Its drivers cover the whole scale path: DuckDB, ClickHouse, Postgres, BigQuery, Snowflake, Databricks — including per-tenant data sources via COMPILE_CONTEXT / driverFactory, which is precisely the BYO-warehouse enterprise story.

The caveat — everything marketed "AI" in Cube is Cloud-only: the Chat API (the old AI API 404s self-hosted), the hosted MCP server (Premium+; the local npm MCP package is deprecated), D3 / "Cube Agentic Analytics", Semantic Catalog, Semantic Layer Sync, and userAttributes in access policies. Plan for the OSS core to be a headless semantic layer and build the agent yourself in LangGraph over REST — which you'd want anyway, since a hosted OAuth MCP can't carry your per-end-user JWTs cleanly. Cube's LTS releases + membership in Open Semantic Interchange (v1.0 spec 2026-01, now incubating as Apache Ossie) keep the model portable if their commercial pivot ever bites.

Division of labor: dbt owns tables, Cube owns metrics. Marts and contracts live in dbt; measures, dimensions, and access policies live in Cube views (with description and meta on every member — that text is literally the agent's prompt context via /v1/meta). Behavioral data

Product analytics: PostHog Cloud as the lens, your warehouse as the truth

The pattern that keeps your open-source stance intact regardless of how PostHog is run: capture once, land raw events in your own warehouse, treat the PostHog UI as a replaceable lens.

"It's open source — do we really need to pay?" No. There are three $0 paths; you pay only for convenience.
(1) Cloud free tier — 1M events/mo with the full funnels/retention/replay UX and zero ops. Even batch exports have a free allowance since the 2025-09 pipelines repricing (1M exported rows + 10k trigger events/mo, then fractions of a cent per row) — so at phase-0 volume the whole Cloud path is $0. Money enters beyond 1M events and for identified-event person profiles. (2) Self-host the MIT "hobby" compose — free forever and data never leaves your infra; the trade is that it's explicitly self-supported (no SLA, no versioned CVE releases, guidance ≤~300k events/mo) and paid-plan features never activate. Its internal ClickHouse is yours, though — a dlt job can pull the raw events table into the warehouse on schedule, replacing the paid export add-on. (3) No product-analytics UI at all — capture via a thin Segment-compatible pipeline (Jitsu, MIT) straight into ClickHouse and rebuild funnels in Superset/Cube: cheapest, most SQL work. Recommendation: (1) for the UX-per-ops ratio while volume is free-tier-sized, with (2) as the principled fallback the day a "no third parties" constraint appears — the warehouse copy makes the switch painless either way.

BI: Superset — one tool, finalized

Decision update: the first draft staged Metabase now → Superset later; per review, we finalize one tool on day one, and it's Superset. Closing the loop

The improvement flywheel: fine-tuned models and a self-tuning agent

Everything upstream of this section is about seeing the product. This section is about feeding what you see back in. Two loops share one substrate — the warehouse plus a pair of registries — and return to production through doors that already exist in NextRole:

  • Loop A — fine-tuned small models: curated trace/outcome pairs train task-specific LoRA adapters that take over the mechanical stages (extraction, parsing, drafting), deployed through the existing main_model/subagent_model runtime overrides.
  • Loop B — the optimizer agent: a second LangGraph agent that reads the marts and traces, and proposes changes to the career agent's prompts, SKILL.md files, tool descriptions, and model routing — as pull requests, never as live edits.

Step zero: own the traces

Traces are the training data — prompt/completion pairs, tool sequences, per-node timings — so they can't live somewhere you can't bulk-read. That rules the current default out: LangSmith's bulk export became Enterprise-only for new signups on 2026-08-03 (existing Plus customers keep it until 2027-02-01), and self-hosted LangSmith was already an Enterprise add-on. The replacement is a gift to this exact stack: Langfuse went fully MIT in June 2025 — tracing, prompt management, LLM-as-a-judge evals, datasets/experiments, playground all OSS (the enterprise key gates only ops extras like fine-grained RBAC, audit logs, SCIM) — and its self-host architecture is web + worker containers over Postgres, ClickHouse, Redis, and S3 — the four services this plan already runs, with bring-your-own instances supported first-class.

The vault keeps the warehouse doctrine intact. This plan's strongest privacy control is that document bodies never land in the analytical warehouse — and fine-tuning doesn't break that rule. Raw samples (prompt/completion text) live in a training vault: a restricted object-storage area holding versioned JSONL datasets, written only by the dataset builder and readable only by training jobs — the tightest ACL in the platform. The warehouse holds the dataset registry (version, filters, counts, content hash, consent proof) and curation marts that point to trace IDs. Only users with training_consent ever enter a dataset; erasure looks up the registry's user→samples map and rebuilds affected dataset versions; model cards record which dataset versions each adapter saw. And for enterprise tenants: no cross-tenant training, ever — structurally (datasets are tenant-keyed) and contractually.

Loop A mechanics — what actually gets fine-tuned

  • Targets, in order of payoff: the mechanical stages where a 1–8B specialist beats a frontier generalist on cost and latency — JD parsing/skill extraction, CV section structuring, match scoring, battlecard drafting. The judgment-heavy stages (recon synthesis, coaching) stay on frontier models longest.
  • Toolchain: curate in dbt (training marts join outcomes × judge scores × consent to trace IDs) → dataset builder as a Dagster asset (JSONL to the vault + a registry row) → Unsloth QLoRA on a rented GPU (Apache-2.0 core; Axolotl/TRL are fine alternatives — torchtune is no longer maintained, avoid) → MLflow 3 for tracking, LLM-judge evals, and the registry (its PEFT flavor stores adapter-only weights) → vLLM with --enable-lora, where each adapter is its own OpenAI-compatible model name.
  • Deployment is a config string: point OPENAI_API_BASE-style config at the vLLM endpoint and set one subagent's subagent_model to the adapter name — the override middleware NextRole already ships does the rest. Rollback is the same string, backwards.
  • Measurement: the adapter's runs land in the same fct_agent_run/fct_message marts, tagged by model — cost, latency, edit-request rate, and judge scores before vs. after are one Cube query.

Loop B mechanics — the optimizer agent

  • Reads (all governed): marts via Cube with an internal service security context; sampled traces from Langfuse's API (scoped and consent-filtered); eval history from MLflow; pipeline health from elementary's tables; the catalog via MCP once OpenMetadata exists.
  • Produces: diffs to prompts, SKILL.md files, and tool descriptions (they're repo files — git is the prompt registry, PRs are the mechanism); model-routing proposals ("move stage X to adapter Y"); few-shot candidates mined from top-judged traces; eval-set additions for every failure mode it finds.
  • Never self-applies. Every proposal is a PR that must pass the offline eval gate (golden questions + trace-replay A/B with the same judges as Loop A) and a human merge — the same HiL philosophy the execute tool already follows. Canary via the runtime configurables; the marts score the canary.
  • Why the metadata investment pays off here: the optimizer's entire worldview is machine-readable surfaces this plan already builds — Cube /v1/meta, dbt manifest/docs, elementary tables, MLflow, the dataset registry. No scraping, no tribal knowledge.

Trust

Governance: dbt as the spine now, OpenMetadata when diligence starts

Governance for a solo-built platform has to be generated, not authored — tags, docs, lineage, and quality results all emitted by the tools you already run, then surfaced by a catalog only when there's an enterprise buyer to show them to.

Horizon 0 (now): the dbt governance spine — $0 extra infra

  • Documentation: description on every model/column; dbt artifacts (manifest.json, catalog.json) are the machine-readable docs an LLM agent can consume directly — alongside Cube's /v1/meta.
  • Contracts: contract.enforced: true + typed columns on every gold model — schema drift fails the build instead of the dashboard.
  • Lineage: dbt manifest (table-level) + the Dagster asset graph (run-anchored, includes dlt sources). That combination answers enterprise "show me lineage" questions without any lineage server. Marquez is dormant — don't deploy it; emit OpenLineage only if a customer's platform demands it (DataHub has a native OL REST sink).
  • Quality: dbt tests on keys/accepted values + elementary for anomaly, freshness, and volume monitoring inside dbt build — results land as warehouse tables the agent can also query ("is this dashboard stale?").
  • PII tags: meta: {pii: true, class: direct|quasi|content} on columns in dbt YAML — the single source that later drives catalog classification and warehouse masking policies.

Which catalog when — the scenario matrix

The catalog question is never either/or with warehouse-native catalogs, because they play different positions: Unity Catalog / Horizon / Dataplex / Purview are enforcement catalogs — they live inside one vendor's engine and actually apply permissions there — while OpenMetadata is a federating catalog: discovery, glossary, PII classification, and lineage across engines, enforcing nothing itself. The portable truth is neither: it's the meta tags and descriptions in your dbt project, which project into whichever catalogs a deployment has.

Rule of thumb: ship projections, not a catalog, into customer environments — their catalog governs their warehouse; OpenMetadata is your view over everything you operate.

PII & GDPR playbook (named patterns)

  1. Tag at source, enforce at warehouse: dbt meta PII tags → catalog classification → tag-based masking where native (Snowflake masking policies via post-hooks, BigQuery policy tags in dbt column YAML); on DuckDB/ClickHouse, mask in silver views instead.
  2. Pseudonymize at bronze: hash direct identifiers in the dlt transform (email → hash + domain, IP → /24); keep the identity map in a restricted vault schema. Still personal data — it narrows blast radius, not obligations.
  3. Content never lands: NextRole's strongest control is structural — CV/JD/chat text is dropped at extraction, so the warehouse holds counts, tokens, and statuses, not documents.
  4. Deletion-requests cascade: a deletion_requests table drives erasure — bronze deletes first, silver/gold rebuild on schedule; plus PostHog person-delete, object-storage prefix-delete (users/<id>/… makes this one call), and the OLTP's own cleanup.
  5. Retention windows: 30–90-day lifecycle on bronze bounds the replay surface and satisfies storage-limitation; gold keeps only pseudonymous aggregates long-term.
  6. Crypto-shredding (per-user keys, erase = destroy key) only if immutable stores/backups enter the picture.
  7. Training is its own lawful purpose: fine-tuning on user content needs an explicit training_consent flag on the user, purpose limitation in the DPA, and erasure that reaches dataset versions (and documents model lineage) — mechanics in the flywheel section.

Horizon 2 (enterprise): BYO-warehouse without a rewrite

The pattern enterprise data vendors converged on is control plane (you) / data plane (customer): your orchestrator runs a parameterized dbt package + dlt pipeline per tenant against credentials the customer grants, into their BigQuery/Snowflake/Databricks — their data never leaves their perimeter, which is exactly what a recruiting company will demand for candidate PII. The design work that makes this a config change instead of a rewrite is already in this plan:

  • dbt project stays a package with no hardcoded schemas/tenants; adapters cover their warehouse.
  • Cube compiles per tenant (COMPILE_CONTEXT) and can point at per-tenant data sources (driverFactory) — same models, their warehouse, same RLS semantics.
  • For shared-SaaS tenants: schema-per-tenant for isolation-sensitive buyers, row-level isolation via the semantic layer for the rest; warehouse-native sharing (Snowflake shares / BigQuery Analytics Hub) when they only want datasets, not pipelines.
  • What buyers will ask for in diligence: SSO/SAML + SCIM, immutable audit logs (Cube query logs + warehouse access logs), SOC 2 path, DPA + subprocessor list (PostHog Cloud appears here — or gets swapped for Jitsu), data residency, documented erasure, and lineage — which is the moment the OpenMetadata deploy pays for itself.

Execution

Roadmap: two weekends to dashboards, then grow on triggers

Phase 0 — the whole stack, day one ≈ 2–3 weekends

  • Compose it: six services join docker-compose.yml — clickhouse, dagster-webserver, dagster-daemon, cube, superset (app + worker) — with Dagster's run storage and Superset's metadata in the existing Postgres and Superset's broker on the existing Redis. Budget 2–4 GB extra RAM on the dev box.
  • Instrument events: the ~15-event taxonomy above via posthog-js + posthog-python (same distinct_id across the boundary), plus the flywheel's labels from day one: thumbs on artifacts, edit-request outcomes, and a training_consent flag on the user.
  • Land it: an analytics/ directory with the dlt pipeline → ClickHouse per the sync plan (content fields dropped at extract); PostHog events arrive by batch export + s3() ingest, or dlt straight from the hobby stack's ClickHouse.
  • Model it: dbt project on dbt-clickhouse — stg_*/int_*/marts per the modeling section, contracts on gold, PII meta tags from the first model; plain dbt tests now, elementary when you want history and alerts.
  • Serve it: Cube Core over gold (metrics + descriptions — the agent's future vocabulary), Superset pointed at Cube's Postgres-wire SQL API.
  • Schedule it: one Dagster daily schedule materializes the whole asset graph — dlt sources → staging → marts (→ elementary) — with retries, backfills, and lineage in the UI from the first run.
  • First deliverables: the activation funnel (upload → processed → tailored → rendered → downloaded), cost per user/model from usage_metadata, run reliability, WAU.

Phase 0.5 — the analytics agent MVP ≈ 1 weekend

  • A LangGraph subagent with two tools: discover_metrics (cached /v1/meta) and run_query (POST /v1/load). NextRole already mints EdDSA JWTs and publishes JWKS for Better Auth — reuse that identity to build the Cube security context, so the agent inherits each user's row-level scope automatically.
  • Read-only by construction (no warehouse credentials in the agent); queryRewrite throws when the security context is missing — fail closed.
  • Ship with a golden-question eval set ("how many runs failed this week?", "what did model X cost per artifact?") so semantic-model changes can't silently break it.

Phase 1 — same stack, its own box on triggers

  • Triggers: laptop RAM pressure, always-on dashboards, >1M events/mo, or the flywheel needing steady compute.
  • Move, don't migrate: the identical compose stack relocates to a VM; ClickHouse gets real disks and backups; add row policies for any human warehouse logins (the engine-side second lock).
  • PostHog checkpoint: outgrown the free tier? Pay, or switch lanes per the decision tree (hobby self-host / pipeline-only capture) — the warehouse copy makes it painless.
  • Flywheel starts: self-host the trace store, build the training marts + dataset registry, run the first LoRA — milestones below, mechanics in the flywheel section.
  • OpenMetadata the moment discovery pain or a diligence request appears (scenario matrix in governance).

Phase 2 — enterprise & BYO warehouse first enterprise deal

  • OpenMetadata catalog: ingest dbt, Dagster, the warehouse, and BI; its PII auto-classification reconciles against your dbt meta tags.
  • Tenant packaging: dbt package with per-tenant vars; Cube COMPILE_CONTEXT + driverFactory per tenant; secrets vaulted per customer.
  • BYO adapters in install-base order (Snowflake → Databricks → BigQuery → Fabric → Redshift), mirroring PII tags into each engine's native masking/RLS.
  • The diligence kit: SSO/SCIM, immutable audit (Cube query logs + warehouse access logs), documented erasure cascade, DPA + subprocessor list, data residency choices.

Flywheel milestones details in the flywheel section

  • F0 (inside Phase 0): the labels exist from day one — thumbs + edit-outcome events in the taxonomy, training_consent on the user, eval golden sets started.
  • F1: own the traces (self-hosted trace store) and build the curation layer: training marts, dataset registry, the consented training vault in object storage.
  • F2: first fine-tune — a LoRA on an extraction-grade task, tracked in MLflow, served on an OpenAI-compatible endpoint, deployed to one subagent via the existing subagent_model override. Classical ML rides the same marts (match-quality scoring, churn propensity) with scikit-learn/XGBoost as Dagster assets.
  • F3: the optimizer agent ships its first prompt/skill PRs behind the eval gate.
  • Governance applies throughout: datasets and features inherit PII tags; no raw-text training without consent; never cross-tenant.
